# ADR 0003: 物理演算ロジックの分散処理における Pandas UDF (Apache Arrow) の採用

「シェフ（Python）」と「運び屋（Arrow）」、そして「巨大なキッチン（Spark）」の連携を最適化し、複雑なスペクトル解析の高速化を実現しました。

  * **科学計算の解放**: Spark標準関数では記述が困難な SNV や 1 次微分などの物理演算を、NumPy/SciPy のまま分散実行可能に。
  * **通信の高速化**: Apache Arrow によるメモリ共有（ベクトル化転送）を採用し、シリアライズのボトルネックを排除。
  * **可読性と性能の両立**: 研究室レベルの高度な解析ロジックを、プロダクション環境の分散処理基盤へシームレスに統合。

-----

## 📝 コンテキスト

スペクトル分析において、**SNV（標準正規変量変換）や数値微分**といった複雑な物理計算は必須の工程です。しかし、これらを PySpark の標準関数（`pyspark.sql.functions`）のみで実装しようとすると、以下の問題が発生します。

1.  **実装の困難性**: 行列演算や窓関数を多用するロジックを標準関数で組むのは非常に複雑。
2.  **可読性の低下**: 物理的な意味を持つ数式が、Spark 特有の DSL に埋もれてしまい、ドメイン知識の継承が困難。
3.  **保守性のリスク**: NumPy 等で検証済みのロジックを、再度 Spark 用に書き直す際のバグ混入リスク。

## 💡 意思決定

物理ロジックの柔軟性と分散処理の圧倒的なスループットを両立するため、**Pandas UDF (Vectorized UDF)** を採用することを決定しました。

## ✅ 帰結

### メリット (+)

  * **科学計算エコシステムの活用**:
    NumPy や SciPy といった強力なライブラリを分散環境でそのまま利用可能。研究・分析フェーズで作成したコードを最小限の修正でスケールアップできる。
  * **Apache Arrow による爆速転送**:
    JVM と Python 間のデータ受け渡しに Apache Arrow を採用。データを「箱詰め（シリアライズ）」し直さず、メモリ上の配置を維持したまま転送することで、従来の Python UDF よりも劇的に高速化。
  * **コードのクリーン化**:
    物理演算ロジックを Python 関数として独立させることができ、テストコードの作成やドメイン知識のコード化が容易になった。

### デメリット / リスク (-)

  * **オーバーヘッドの存在**:
    JVM と Python プロセス間の通信コストはゼロではない。
  * **設計上の制約**:
    通信コストを最小化するため、可能な限り一括処理（Batch処理）を行うデータ構造とし、データの「行き来」を減らすパイプライン設計が求められる。

### 🚀 実装への反映

本決定に基づき、`src/features.py` 内の SNV 補正および 1 次微分ロジックはすべて `pandas_udf` デコレータによって実装され、24コアの並列リソースをフルに活用した高速演算を実現しています。
