# ADR 0002: Java 21 (LTS) への移行と実行環境のモダン化

「最新の土台（Debian Trixie）」に「最新のエンジン（Java 21）」を。インフラの世代交代により、長期的な安定性とパフォーマンスを確保しました。

* **LTS世代の採用**: Debian Trixie において提供が終了した Java 17 に代わり、最新の長期サポート版である Java 21 を導入。
* **互換性の検証**: Spark 3.5.0 と Java 21 の組み合わせにおける動作検証を完了し、次世代の分散処理基盤を構築。
* **将来の負債解消**: パッケージ管理の制約を逆手に取り、インフラ構成を強制的にモダン化することで、将来的な技術負債を未然に排除。

---

## 📝 コンテキスト
本プロジェクトの分散処理基盤として採用している Docker イメージ（Debian Trixie ベース）において、旧来の推奨環境であった Java 17 の公式サポートおよびパッケージ提供が終了しました。これに伴い、実行環境の再設計を余儀なくされました。

## ⚠️ 課題
1.  **依存関係の断絶**: 
    Debian の次世代レポジトリにおいて Java 17 が非推奨・削除され、標準的な `apt-get` による環境構築が不可能となった。
2.  **エコシステムの不確実性**: 
    Apache Spark 3.5.0 と最新の Java 21 の組み合わせは、パフォーマンスや安定性の面で実証データが比較的少なく、慎重な検証が求められた。

## 💡 意思決定
一時的なワークアラウンドで Java 17 を維持するのではなく、**Java 21 (LTS) への全面移行**を決定しました。

1.  **LTS路線の堅持**: 
    プロダクション利用を見据え、短期的なバージョンではなく長期サポートが保証された Java 21 を選択。
2.  **マルチステージビルドの最適化**: 
    Docker レイヤーで Java 21 と Spark 3.5.0 の依存関係を再定義し、クリーンかつ軽量な実行環境を再構築。

## ✅ 帰結

### メリット (+)
* **最新スタックによる恩恵**: 
    Java 21 の最新 JVM 特性を活用可能になり、メモリ管理やスループットの向上が期待できる。
* **環境の陳腐化防止**: 
    最新の OS（Debian Trixie）と最新の Java を組み合わせることで、今後数年間にわたる安定した開発・実行環境を確保。
* **トラブルシューティング能力の向上**: 
    この移行過程で発生したメモリ制限問題を ADR 0004（JVMオプションの注入）で解決したことにより、インフラ層への理解が深化した。

### デメリット / リスク (-)
* **実行時オプションの複雑化**: 
    Java 21 の厳格なカプセル化に対応するため、Spark 起動時の JVM オプション設定が必須となった（詳細は ADR 0004 参照）。

### 🚀 実装への反映
本決定に基づき、Dockerfile のベースイメージおよび Java インストールプロセスを刷新しました。これは、単なる「動かなくなったから直す」対応ではなく、プロジェクト全体の技術スタックを最新世代へと引き上げる戦略的なアップデートとなりました。
