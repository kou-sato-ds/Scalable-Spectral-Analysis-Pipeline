# ADR 0001: Apache Spark による分散処理基盤の導入とコンテナ化

「スケーラビリティの確保」と「環境の完全再現」を掲げ、将来的なデータ増大に耐えうる解析基盤の初手を打ちました。

* **メモリの壁を突破**: 単一マシンの限界に依存せず、ノードの追加（スケールアウト）で対応可能な分散処理構造を定義。
* **「動かない」の殲滅**: Docker によるインフラのコード化（IaC）により、チーム開発やクラウド移行時における環境不整合を排除。
* **最新スタックの選定**: Spark 3.5.0 × Java 21 を基軸とし、モダンなデータエンジニアリングの標準を確立。

---

## 📝 コンテキスト
1,500次元を超える超高次元スペクトルデータを取り扱う本プロジェクトにおいて、将来的なデータセットの肥大化（スケーラビリティ）を見越した設計が不可欠でした。また、OSやライブラリのバージョンに依存する「私の環境では動く」という問題を根本から解消し、実務レベルの再現性を確保する必要がありました。

## 💡 意思決定
以下の 3 つの柱をプロジェクトの技術基盤として採用することを決定しました。

1.  **データエンジン**: **Apache Spark (PySpark) 3.5.0**
    * 大規模データに対するベクトル演算および並列処理を実現。Pandas UDF による高度な特徴量生成を可能にする。
2.  **インフラ**: **Docker / Docker Compose**
    * Master ×1, Worker ×2 のマルチノード構成をローカル上に擬似再現。環境をパッケージ化し、ポータビリティを担保する。
3.  **実行環境**: **Java 21 (OpenJDK)**
    * Debian ベースの Python 3.11 環境において、最新の LTS 世代としての安定性と将来性を重視。

## ⚖️ ステータス
**Accepted** (2026-04-05)

## ✅ 帰結

### メリット (+)
* **水平スケーラビリティ**: 
    数万件〜数百万件のデータに対しても、Worker を追加するだけで処理能力を拡張可能。
* **クラウド・ネイティブ**: 
    Docker 基盤を前提とすることで、AWS EMR や Glue などのマネージド環境への移行パスが極めてスムーズになった（※ADR 0005 にて実証）。
* **厳格なバージョン管理**: 
    Java や Python、Spark のバージョンがコード（Dockerfile）で固定され、チーム全体での一貫性が完全に保証された。

### デメリット / リスク (-)
* **リソース・オーバーヘッド**: 
    Docker Desktop の起動コストおよび、コンテナ実行によるホストマシンのメモリ消費が発生。
* **学習コスト**: 
    分散処理特有の概念（RDD, DataFrame, Lazy Evaluation）やコンテナネットワークへの理解が、開発メンバーに求められる。

### 🚀 実装への反映
本 ADR の決定に基づき、プロジェクトルートに `Dockerfile` および `docker-compose.yml` を配置。Master/Worker 構成を立ち上げるだけで、即座に 24 スレッドをフル活用できる「最強の解析環境」がデプロイされる仕組みを構築しました。
