「最新鋭の設備（Java 21）」と「最大火力（24コア）」を両立させるための配管工事を完遂しました。

Java 21の突破: セキュリティで閉じられたメモリ領域を、--add-opens オプションで「特例承認」として開放しました。

24コアの解放: Workerを増設し、マシンの全リソースをSparkにリンクさせることで、計算速度を劇的に向上させました。

環境の抽象化: これらの複雑な設定をすべてDockerfileに封じ込めたことで、誰がどこで動かしても同じ「最強の計算環境」が立ち上がるようになりました。


ADR 0004: Java 21 / Spark 3.5.0 におけるインフラ基盤の最適化と並列処理リソースの最大化 詳細

コンテキスト
SIGNATE「スペクトル分析チャレンジ」において、1,500次元を超える高次元データに対する特徴量エンジニアリングを高速化する必要があった。

また、最新の LTS (長期サポート) 世代である Java21 を採用し、将来的な保守性とセキュリティを確保しつつ、Apache Spark の分散処理能力を最大限に引き出す必要があった。

課題
1. Java 21 の強固なメモリ保護: Java 17 以降、特に Java 21 では JVM のカプセル化が強化され、Spark や Apache Arrow が内部メモリ (java.nio) に直接アクセスできず、UnsupportedOperationException をスローしてクラッシュする。
   
2. ライブラリの互換性: NumPy 2.x へのメジャーアップデートに伴う API 変更 (np.trapz の廃止) への対応。

3. 計算リソースの不足: 初期設定の 12コア (1 Worker) では、3,000次元超の特徴量生成に時間を要していた。

意思決定
以下の技術的アプローチを採用することを決定した。
1. JVM チューニングの外部注入: Dockerfile および Docker Compose レイヤーでJDK_JAVA_OPTIONS を定義し、--add-opens フラグを用いて特定の内部パッケージへのアクセスを許可する。

2. Worker ノードの増設: コンテナオーケストレーションにより Worker を 2 台に増やし、ホストマシンの物理限界である 24コアを活用する。

3. 互換性レイヤーの実装: 特徴量抽出ロジックにおいて、ライブラリのバージョンに依存しない動的なメソッド呼び出し (hasattr による判定) を採用する。

構成
Dockerfile (JVM 設定)
ENV JDK_JAVA_OPTIONS="--add-opens=java.base/java.nio=ALL-UNNAMED
--add-opens=java.base/sun.nio.ch=ALL-UNNAMED"

並列リソース設定
- Master: 1基
- Worker: 2基 (各12コア)
- Total Cores: 24 Cores
  
帰結
メリット
- 高速化: 24コア並列処理により、全 Fold の学習および特徴量生成時間が大幅に短縮された。

- 堅牢性: Java 21 という最新の実行スタックにおいても、Spark のパフォーマンスを損なうことなく安定稼働することを確認。

- 再現性: インフラ設定を Docker 内にコード化 (IaC) したことで、他環境でも即座に「最強のキッチン」を再現可能になった。

デメリット / リスク
- リソース競合: ホストマシンのリソースをフルに使い切るため、実行中は他の重いタスクとの並行が困難。
